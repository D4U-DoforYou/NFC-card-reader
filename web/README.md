# D4U · Web（Web Bluetooth / USB）

用**桌面浏览器**给墨水屏标签刷图，并提供通用 NFC 读写、画板与火车票生成。

```bash
cd web
npm install
npm run dev      # http://localhost:5180
npm run build    # 产物在 web/dist，纯静态，可直接丢到任何静态服务器
```

发布到 GitHub Pages 的 `web_github_pages` 分支：

```bash
./scripts/push-github-pages.sh
```

脚本会执行类型检查和生产构建，只把静态产物推送到 `D4U-DoforYou/NFC-card-reader` 的 Pages 分支；需要本机已配置该仓库的 Git 推送权限。

纯前端，**没有后端**。路由用 hash 模式，静态托管不用配重写。

## 硬件方案与兼容范围

已登记两个硬件方案：

| 方案 | 广播名 | 通信协议 | 目录 |
| --- | --- | --- | --- |
| A01 | `D4U-NFCA01-XXXX` | `core/protocol/a01` | `core/protocol/a01` |
| B01 | `D4U-NFCB01-XXXX` | 目前与 A01 一致 | `core/protocol/b01` |

- 最新设备协议以 `tmp/rf_device_platform-python/protocol/device.proto` 与 firmware / host 实现为准。
- 广播名的后缀是蓝牙 MAC 的十六进制尾段，长度随固件而异。方案不支持时拒绝连接，不回退到别的方案。
- A01 的 UUID、COBS / CRC32、Protobuf、作业会话和 RF 预设都在 `core/protocol/a01`；公共层通过硬件档案与 `DeviceSession` 使用它们。
- **B01 目前通信协议与 A01 一致**：档案独立，会话实现复用 `A01Session`。协议一旦分叉，只改 `core/protocol/b01`，上层不动。
- 支持功率档位 0–3 的设备读取与设置；重新进入连接页会重新读取，不复用旧设备值。
- ISO-DEP 使用向上取整的毫秒等待，WTX 按倍数延长下一帧等待，多段响应完整拼接。
- Type A 的 SAK=00 是有效的非 ISO-DEP 选卡结果。ATQA 44 00 与旧表示 00 44 可进入 NTAG / Ultralight；型号与容量可进一步通过 Type 2 CC / GET_VERSION 确认。
- Type 2 支持分页、CC、NDEF 读取。NTAG 21x / I2C 的短文本写入限制在页 4–15，保留 UID 确认、静态锁检查、长度最后提交和回读校验；未知布局不自动写入。
- raw RF 1.2 的芯片命令 / FIFO 与寄存器接口已适配；旧固件不会尝试这些操作。
- MIFARE Classic 1K（SAK 08）支持使用已有 Key A / B 认证并读取 16 字节数据块；写入仅限数据块，保留 UID 复选和回读校验。Crypto1 与加密奇偶校验由 CLRC663 执行。
- 拓竹料盘可按当前 UID 派生扇区 Key A，一键读取材质、颜色、重量、温度与生产信息；支持 4 字节 UID 的 Classic 1K 标签。
- 支持 BLE OTA：检查应用镜像与目标芯片，发送 SHA-256、按 512 字节分块计算 CRC32 并等待 ACK，全部确认后才请求切换。传输异常不自动重发。
- Type B / FeliCa / Type V 支持协议探测和原始帧。
- USB HID 控制接口 VID/PID 为 `1A86:572D`，浏览器通过 8 字节厂商报告传送与 BLE 相同的 COBS / CRC32 协议帧。

回归验证：`npm test`；类型检查与生产构建：`npm run build`。测试使用模拟设备，不代替真实设备 + 卡片联调。
识别规则参考 [NXP AN10833](https://www.nxp.com/docs/en/application-note/AN10833.pdf)；ATQA / SAK 只能提供型号候选，不能唯一确认所有芯片。

## 自动休眠（B01）

B01 的升压电路在**射频场关闭时负载太轻，供电会自行断掉**，设备随即掉电。所以这类设备不能像 A01 那样「关场就不管」，闲时改用短脉冲保活。

网页端调度，固件不用改——射频场本来就能用 `setRfField()` 完整开关。

| 开关 | 行为 |
| --- | --- |
| 自动休眠**开**（默认） | 闲时每 10 秒把射频场打开 1 秒再关掉，这个脉冲循环只维持 10 分钟；10 分钟内没有任何操作就停掉脉冲，设备进入深睡，等下一次操作再唤醒 |
| 自动休眠**关** | 同样的脉冲循环持续下去，设备永远不休眠 |

- 脉冲**只在闲时跑**：刷图和通用 NFC 通信期间射频场保持开启，调度器不插手（刷图用 `retainField()` 挂住，通用 NFC 按 `busy` 挂住）。
- 脉冲**不会抢着关场**：这一秒里只要设备被用过（刷图、读卡、手动开场），
  脉冲就把关场交给空闲定时器——中途关场会把正在进行的通信打断，卡片当场复位，
  表现出来就是「通信中断」。
- 深睡窗口**只在有真实射频活动时重置**。脉冲自己开关场不算活动，否则设备永远醒着，「自动休眠」就名存实亡了。
- 手动打开射频场时（1 分钟倒计时）调度器让路，不抢着脉冲。
- 开关状态存在 `localStorage`，连上设备后生效；连接页 02 区块能看到实时状态（下次唤醒倒计时、剩余深睡窗口、是否已休眠）。
- 只对声明了 `supportsAutoSleep` 的硬件方案生效。目前只有 B01 声明，A01 保持原来的「空闲 8 秒关场」。

实现见 `core/rf/autoSleep.ts`（只管时序，射频场怎么开关由驱动注入，因此能脱离真机做回归测试）。

## Classic 1K 与芯片原语

1. 在「通用 NFC → 卡片」识别目标卡，然后进入「存储」。
2. 选择「单块读取」或「扇区读取」。点击扇区地图可直接选择 0–15 号扇区，也可用下拉框切换；输入该扇区的 Key A / B（12 位 HEX，明文显示）。单块模式保留块号 0–63 的读取。
3. 扇区模式默认读取前三块，可勾选「包含访问控制块」读取完整四块；扇区 0 的前三块含厂商块。扇区内只认证一次，结果按块显示类型、HEX 和 ASCII，另提供连续 HEX。访问控制块的实际内容受卡片权限限制。
4. 手动读取与工具箱共用读取流程：遇到射频错误时，重新选卡核对 UID，使用原密钥重读一次；持续失败则停止。
5. 写入面板单独显示目标块号；使用认证面板中的密钥，填写恰好 16 字节，确认 UID、块号和新数据后执行。块 0 和各扇区尾块不能写入。失败不会自动重发。

本功能需要设备声明 `org.example.rf.raw` 1.2 及 `execute_command` / `read_register` / `write_register`。密钥只保存在当前页面内存中，不写入日志或浏览器存储。当前适配范围是 1K；其他 Classic 容量保留识别和地图。
「原始」页的折叠面板提供芯片命令与寄存器调试；命令白名单、寄存器保护范围与 A01 固件保持一致，执行芯片命令需绑定已识别 UID。

## 拓竹料盘

先在「通用 NFC → 卡片」识别料盘标签，然后进入「工具 → 工具箱 → 拓竹料盘 · 通路验证」点击「开始验证」。无需填写参考表中的密钥：程序使用当前 UID，通过 HKDF-SHA256 派生各扇区的 Key A。实现与格式依据 [Bambu Research Group 的公开研究](https://github.com/Bambu-Research-Group/RFID-Tag-Guide)。

读取块 1、2、4、5、6、9、12、14；同一扇区复用认证。射频错误时仅重读该扇区一次，先重新选卡并核对 UID；不会自动写卡或换用其他密钥。读取后清除内部密钥数组，工具箱保留本次使用的扇区、块号和 Key A（12 位 HEX），同时标明 UID、HKDF-SHA256、Salt 与 Info。显示的密钥仅留在本页内存中，重新识别、断开或离开页面后清除，不写入日志或浏览器存储。结果展示耗材信息，原始数据可在「数据详情」查看。格式校验不等于 RSA 真伪验证。

已用真实 A01 / 固件 0.2.1 / 料盘 UID `56 0C AE E9` 完成浏览器端 8 块读取，参见[实物验证记录](docs/classic-hardware-verification.md)。本机实测发现 A01 原接收增益较高时认证不稳定：Classic 会话现临时降低接收增益，结束后恢复；修正后四扇区 12 次认证回读、浏览器手动读取 5 次及完整料盘读取通过，未触发重读。此验证仅覆盖当前设备、卡片和摆放，不代表所有射频环境。

## 固件 OTA

在「连接设备 → 固件升级」选择 **A01 / ESP32-C3 的应用 `.bin`**，查看项目与版本信息，再点击「上传并升级」。不接受 bootloader、分区表或合并烧录镜像；最终镜像与分区容量校验由设备执行。

OTA 未提供独立能力声明，因此以设备对 `TransferBegin` 的响应判断是否支持。旧固件返回不支持时，需先通过有线烧录具备 OTA 与双分区的固件。
上传期间其他设备操作被锁定；停止或失败后需重新连接。切换阶段不能中止，切换应答不确定时不会自动重发。成功应答仅表示设备接受了升级；重连并读取版本后才能确认新固件已运行。

## 浏览器要求

| 能力 | 要求 |
| --- | --- |
| 蓝牙 | Chrome / Edge 桌面版（Web Bluetooth）。Safari / Firefox 目前不支持 |
| USB | Chrome / Edge 桌面版（WebHID，VID/PID `1A86:572D`） |
| 画布 | 需要 `OffscreenCanvas`（Chrome 69+）；缺失时模拟屏显色动画会退化为整幅渐显 |

蓝牙与 USB 都**必须由用户手势触发**，所以「连接」永远是点按钮弹系统对话框，不能自动连。

## 设备协议

网页端用的是 `tmp/rf_device_platform-python` 定义的版本化协议：
Protobuf 承载消息，COBS + CRC32 承载帧，走 BLE GATT。

### 硬件方案隔离

蓝牙广播名规则：

```text
D4U-NFC + 硬件方案编号 + '-' + 蓝牙 MAC 尾段
例如 D4U-NFCA01-1A2B、D4U-NFCB01-30CEF9F517
```

- `D4U-NFC` 是固定前缀，所有方案共用；
- `A01`、`B01` 是硬件方案编号，**协议差异按方案隔离**：
  以后出 A02，协议可能不一样，就在 `core/protocol/` 下另建一个目录，
  上层（射频桥、界面）不用改；
- 末尾是蓝牙 MAC 的十六进制尾段，**长度随固件而异**（1–6 字节）：
  A01 广播后两字节，B01 广播 5 字节。解析只校验「是十六进制且不超过 6 字节」，
  方案号才是认设备的依据。

`core/protocol/hardware.ts` 是方案登记处：名字认得出方案就按方案走；
名字认不出（被改名、被截断）就按 GATT 服务反查。
**认不出的方案不会退而求其次去用别的方案的协议**——宁可连不上，也不能
拿 A01 的协议去硬碰一台说不清话的设备。

新增一个方案要做三件事：

1. 在 `core/protocol/<方案>/` 下写档案（`scheme` / `label` / GATT UUID /
   射频预设 / `createSession`）；
2. 在 `core/protocol/hardware.ts` 的 `PROFILES` 里登记；
3. 在 `core/protocol/index.ts` 里导出档案。

协议暂时与已有方案一致时，可以直接复用那边的会话实现（`b01` 就是这么做的），
等协议分叉了再在方案目录里单独实现——上层永远不用改。

### 帧格式与消息

```text
原始帧 = len(4B 小端) | protobuf 负载 | crc32(负载)(4B 小端)
线上帧 = COBS(原始帧) | 0x00
```

- 帧与帧之间用 `0x00` 分隔，设备收到字节流即可自行切帧，
  所以一帧拆成多次 BLE 写入也不会错位；
- 写入被拒时，发一个 `0x00` 让设备丢掉残留的半帧，再调小单包上限整段重写；
- 消息契约是 `rfplatform.v1`：握手（Hello）→ 能力清单（CapabilityList）→ 作业（StartJob / JobEvent）。

实现与固件逐字节对齐，`tests/a01-protocol.test.mjs` 直接拿固件仓库里的
测试向量（`protocol/test_vectors/*.hex`）比对。

## 传输层

上层（射频桥、刷图、读卡）完全不关心底下走的是蓝牙还是 USB：
传输层只搬运**字节**，帧的切分与消息的解析都在 `core/protocol` 里按硬件方案完成。

### 蓝牙（Web Bluetooth）

- GATT 布局与 A01 固件一致：服务 `FF10`、写特征 `FF11`、通知特征 `FF12`。
- 浏览器蓝牙**没有持续扫描**，只能由用户手势弹出系统设备选择器，
  所以网页端的「附近读卡器」列表换成了「选择设备」；
  浏览器也**不提供 RSSI**，连接页的信号一律显示「信号未知」（不拿别的数字冒充）。
- **有限窗口确认**：特征值支持无响应写时，每帧最多连续发送 3 片，
  第 4 片及帧尾等待 ATT 确认，减少逐片等待连接间隔的开销并限制设备接收队列深度。
  若发生静默丢帧，窗口会从 4 片逐步收窄；收窄到 1 片后改为逐片确认。
  不支持无响应写的特征值始终逐片确认。
- **写入上限取已知安全值**：设备发帧分片和浏览器报告的
  `maxWriteWithoutResponseSize` 可以提供安全上限；还没有这两项信息时使用
  保守的 20 字节。B01 会额外用只读能力查询验证 118 字节候选值；只有完整回包匹配后才提高上限，失败则重同步并确认链路恢复，不试更大的长度。
- **统计同一阶段**：链路计数与协议分段只覆盖图像上传，排除刷新状态查询，
  与“传输耗时”使用相同起止点。
- **部署和限制**：参见 [BLE 传输排查](docs/ble-transfer-speed.md)。
- **掉线必须当场发现**：`gattserverdisconnected` 监听在 `gatt.connect()` 之后立刻挂上，
  连接过程中掉线也要报错——否则连接流程会一路走到最后，把一条已经断掉的链路报成「已连接」。
  链路一断，所有后续操作统一报「读卡器已断开…请重新连接」，
  而不是把浏览器的英文原始异常甩给用户。
- **写入有上限**：浏览器的 GATT 写有可能既不成功也不失败——Promise 永远不落地。
  那一次写入就会把整条串行队列堵死：射频场一直开着，后面所有操作都排在它后面，
  看起来就像「传输卡住」。单次写入超过 5 秒即判失败并给出中文提示。
- **「读卡器忙」不是链路坏了**：Chrome 在上一个 GATT 操作还在途时会报
  "GATT operation already in progress"，这是排队。按 60/180/450 毫秒三档退避重试，
  重试期间链路状态不变，不会误报断线。
- **丢片是静默的，帧要自己确认**：固件在应用层丢字节时浏览器不报错，设备也只收到半帧。
  协议层在帧写完后等 1.5 秒：设备一个字节都没回，
  就判定这帧压根没送到——设备没见过它，整帧重发是安全的（不会把操作执行两遍）。
  最多整帧重发 2 次，仍没送达就报「帧未送达设备」而不是干等满 10 秒超时。
  刷图日志里的「整帧重发」计数就是看这个的：次数多说明链路在丢片。

### USB HID

连接方式与蓝牙共用 `DeviceSession` 和 A01 / B01 协议。浏览器筛选 VID/PID `1A86:572D`，
通过 report ID 0 的 8 字节输入 / 输出报告传送协议字节流。协议帧仍由 COBS 编码并以 `0x00`
分隔；输出按 8 字节切片补零，输入报告拼接至分隔符后交给协议层解码。

连接页会在连接后自动执行协议握手、读取设备详情与能力清单。NFC、显示屏和固件升级等操作
通过已有的设备会话执行。浏览器需要支持 WebHID，且页面必须运行在 HTTPS 或 localhost。

## 已知限制

- **只有蓝牙/USB 两条路，没有 WebSocket 之类的远程转发**：浏览器不允许网页直接开串口或
  原始 TCP，跨机连接需要额外的本地服务。
- **浏览器蓝牙不能后台扫描**，也没有「自动连接上次的设备」；
  每次都要用户点一下并重新选择设备（`getDevices()` 拿回来的授权设备也不代表能免选择）。
- **EXIF 方向**：网页端由浏览器解码 JPEG 时自动摆正；
  旋转控件仍从 0° 起算，传送数据仍额外补偿 180°（倒装屏幕）。
- **Classic 真实读写目前只适配 1K**：需要 raw RF 1.2 和已有的扇区密钥。工具箱中的模拟密文分析与真实芯片认证是不同功能，不能用模拟候选证明真实卡片密钥正确。
- **Type B / FeliCa / Type V 只做识别**：A01 固件提供了 19 组收发预设，
  协议探测会逐个协议用自己的模式去问，但后续的读卡流程目前只做了 Type A 与 Type 2。


### 刷图协议同步（2026-11-14）

依据 `tmp/rf_device_platform/host/src/rf_platform/display/` 与 `nfc/iso_dep.py`：

- 华为 C2：双次 PIN 验证；2000 字节压缩块、最多 250 字节 D3 子包；D3 交换限时 20 秒，D4 和显色轮询各限时 120 秒。
- Reink Case C1 1.0：仅 240×416 四色竖屏；使用 D3 压缩上传（不根据 PIN 是否启用选择 D2），每块压缩数据最多 246 字节。超限在上传前提示选择纯色量化或简化图片。D4 最长等待 190 秒，成功响应表示显色完成。
- 按用户要求启用 D3 当前包重传：可恢复射频错误或交换超时后等待 150 ms，重新协商 ISO-DEP，再发送相同块号、子包号的数据，每包最多共 3 次。状态字拒绝、断线不做当前包重传；重新协商失败或包重传耗尽后，Web 对可恢复射频错误等待 1 秒，重新激活并核对 UID、面板参数后从第 0 块重新上传当前图片，最多共 3 次；运行日志记录每次重试，传输进度重新开始。D4 或显色轮询失败不自动重刷。ISO-DEP 保留有界 R-NAK/WTX 恢复，整次交换共享截止时间。完整、CRC 正确且没有其他射频错误的 ISO-DEP 响应允许单独 MINFRAMEERR。
- D1 UID 必须匹配选卡 UID，上传前检查 PIN 长度、点阵长度和目标 UID。协议适配仍保留在硬件传输层与屏幕协议层。

以上通过模拟设备与协议回归测试；本次同步未进行实物刷屏或固件升级。


蓝牙兼容性：A01 的 FF10/FF11/FF12 UUID 未变。新固件 FF12 仅声明 Indicate，Web 同时兼容 Notify/Indicate，并通过 `startNotifications()` 订阅；Indicate 连接优先使用有响应写，与参考 Python host 一致。连接日志显示实际订阅和写入方式。

A01 固件 0.2.2 的 BLE 发送队列容量为 4 帧。Web 按完整作业串行执行：收到终态事件后才发送下一个作业，避免设备详情、功率、关场等并发作业的 ACCEPTED/RUNNING/COMPLETED 事件导致 `frame_tx_failed reason=queue_overflow`。回归测试模拟 4 帧队列及延迟 ATT 确认；此项未进行实物验证。


刷图生命周期补充：图片处理、传输、显色期间保持射频场，不受 8 秒空闲关场或手动开场到期影响；作业退出后统一释放并关闭射频场、清除选卡缓存。显色动画按协议成功/失败结果结束，刷新失败显示错误，不得继续写入“显色完成”；新一轮刷写重新选卡并重置步骤。已通过模拟 D4 失败及随后成功重试的浏览器验证，未进行实物测试。

刷图字节统计：每次刷图在运行日志里写三行，方便核对传屏数据。①「图像处理」给出原图尺寸、屏幕尺寸与色数，以及处理后的点阵字节数与每像素位数；②「传屏数据」给出点阵字节数、压缩后字节数与占比（未压缩路径直说与点阵等长）、拆成的包数、包类型（D2 / D3）、单包载荷字节区间与含包头的协议总字节数；③「链路写入」给出本次实际写入链路的字节数、写入次数与单次写入上限（含协议分帧开销），蓝牙单次只能写 ATT 分片大小的字节，这个数能直接看出传输有多慢。统计由 `core/epd/stats.ts` 汇总，华为四色、通用面板 D2 与 C1 压缩三条路径共用同一套口径。

刷图分包边界是**固定 250 字节**，不能按 ISO-DEP 的帧长调整（`tmp/demo_old/README.md` 写明「D3 应用分片大小遵从标签参考协议固定为 250B，不能按 FSC 改变 LZO 分片边界」）。标签按这个固定边界重组 D3 压缩流：把子包改小（比如 246），标签拼出来的就不是合法 LZO 流，解压直接失败并回 `SW=6992`——实测踩过一次。一个 257 字节的 D3 包由 ISO-DEP 按 FSC 拆成多个 I-block 发送，这是协议本来的分层方式。因此应用分包策略遵守标签协议；具体速度差异需要结合实际 BLE 写入长度、写入次数和作业耗时判断，不能仅凭短通知长度推断真实 MTU。

C1 固件 1.0 不接受跨 ISO-DEP 帧的 D3（整块压缩结果必须 ≤246 字节）。现在上传前会先检查当前会话一帧能不能装下整个 C1 包，装不下就**直接拒绝上传并说明原因**，而不是发过去让设备拒收、白占一轮传输时间。


设备能力诊断：握手完成后，Web 按设备公布的能力 ID、主版本与操作名检查功率、射频等请求。仅提供设备信息的固件仍可连接查看详情，但功率设置禁用、刷图在选卡前停止。参考 A01 固件仅在 CLRC663 初始化成功后注册功率与原始 RF 能力；注册失败也应结合串口日志判断。若能力已公布但执行返回 `unsupported capability`，日志标记契约不一致并附带能力 ID、操作名。连接页记录本次能力清单、固件版本与控制器，供间歇故障定位；该诊断不会重放修改操作。

## MIFARE Classic 安全审计

NFC 页的「工具」页签里就是这套东西（原来的「关联密钥分析 / 字典穷举分析 /
模拟数据加解密」三个功能被它替掉了——那三个都属于离线 Crypto1 模型，
在芯片做认证的固件下根本算不出真结果，见下文「做不到的两件事」）。

### 内置密钥字典

一键解举内置 78 条常见默认／弱密钥：出廠默认的 `FFFFFFFFFFFF`、
NXP 的 MAD 密钥 `A0A1A2A3A4A5`、NDEF 密钥 `D3F7D3F7D3F7`、
重复数字与递增序列、以及门禁／公交卡里常见的英文单词密钥
（VMSTAR、SYSTEM、master、pass…）。也可以粘上自己的字典一起跑。

### 为什么主机不用自己算 Crypto1

CLRC663 芯片自己做 MIFARE 认证：`LOADKEY` 装进扇区密钥，`MFAUTHENT` 让芯片
跑完整个握手。握手成功后芯片会自动加密发出的帧、解密收到的帧，
所以主机既拿不到密钥流，也不需要密钥流——审计工具只需要知道「认证成没成」。

固件把这套能力放在 `org.example.rf.raw` 1.2（`execute_command` /
`read_register` / `write_register`），网页端要先确认设备声明了它。

### 工具

| 工具 | 对应 pm3 | 说明 |
| --- | --- | --- |
| **一键解卡** | `hf mf autopwn` | 逐把候选密钥真卡认证，命中就解开扇区并读出。密钥来源可选内置字典／只用自己的字典／两者合并。带进度条、剩余时间估算与实时预览（解开的扇区、密钥、已读出的数据块） |
| **密钥检测** | `hf mf chk` | 拿一把密钥扫全卡，看它能打开哪些扇区 |
| **指定扇区穷举** | `hf mf brute` | 只针对一个扇区逐把试，带进度与中断 |
| 扇区密钥表 | `hf mf fchk` | 16 个扇区的 Key A / Key B，可直接改；「读整卡」按这张表逐扇区读 |

写卡与格式化都会先弹确认框：这两种操作不可撤销。

### 解卡有多快

一把候选密钥要完整跑一遍「复位射频场 → 选卡 → 装密钥 → 认证」，
每个环节都是一次蓝牙往返，所以一把密钥约 2 秒。真机实测（2026-11-15，
UID `560CAEE9` 的 MIFARE Classic 1K）：

| 场景 | 提速前 | 现在 |
| --- | --- | --- |
| 试一把**对**密钥 | 2100 ms | 1594 ms |
| 试一把**错**密钥 | 约 3500 ms（白跑两遍） | 1600–2000 ms |

提速做了四件事：

- **已知 UID 时直接 SELECT**：SELECT 帧自带卡号，只有「学卡号」才需要防冲突
  那一轮射频往返，批量认证时省一次往返。
- **去掉认证前那次「清状态寄存器」的寄存器写**：复位射频场时固件的关场动作
  已经把状态寄存器清零了（等价于 `mfrc630_MF_deauth`），多写一次就是多一个
  蓝牙往返。
- **分清「卡拒了握手」和「卡没应答」**：错密钥时卡回 4 位 NAK，芯片的错误
  寄存器是 `MINFRAMEERR(0x10)`；卡没应答才是 `NODATAERR(0x08)`，收到坏帧
  是 `INTEGERR(0x03)`。只有「卡明确拒了握手」才不重试——之前一律重试，
  等于每把错密钥都跑两遍。作业失败时固件不把错误位带回来，网页端自己读
  一次寄存器（0x0A）来分。
- **不再降低接收增益**：增益一低，芯片就收不到卡回的 4 位 NAK，错误寄存器
  是空的，又得分不清上面那三种情况（实测错误密钥耗时从 1972 ms 变成
  3986 ms）。

另外候选先试完 Key A 再试 Key B——大多数卡的读写都用 Key A，命中能早一半。

### 做不到的两件事

- **HardNested / Nested 密钥恢复**：这两种攻击都要拿卡发出的随机数 nT 和
  加密后的 nR。认证由芯片完成，主机根本看不到这些数据，所以没法做。
  固件要支持，得再开一条「主机自己做认证」的通路。
- **MFOC 式的离线破解**：同理，离线解密的输入（密钥流中间态）主机拿不到。
  现有的离线 Crypto1 工具只能处理外部导入的挑战数据。

能落地的是**在线字典穷举**：候选密钥逐把真卡认证，命中即用。
这正是 MFOC 的实际工作方式——先恢复密钥，再整卡读出。

### 访问权限怎么解

尾块布局是 Key A(6) | 访问位(3) | GP(1) | Key B(6)，12 个条件位分两份存
（真值与反码），反码对不上说明这张尾块已经写坏了——这种尾块再往卡上写
可能把整个扇区锁死，所以工具会单独报出来。

判定与 Proxmark3 完全对齐（`mfGetAccessConditionsDesc` /
`mfValidateAccessConditions`），并且认得出三种常见配置：
运输配置 `FF0780`、启用 Key B 配置 `7F0788`、禁用值块命令配置 `787788`。

### 认证失败怎么读

控制器只会报「射频错误」，**不能据此断言密钥错了**——卡没应答和握手被拒在
报错上长得一样。只有「芯片没报错、但也没建立 Crypto1 会话」才能说明密钥没被接受。

真机实测出来的几条约束（都写在 `core/nfc/mifareClassic.ts` 里）：

- `MFAUTHENT` 的等待时间要给到 **300 ms**。100 ms 时卡片应答慢一点就报
  `NODATAERR|PROTERR`，认证会被误判成失败。
- 选卡先试 **REQA(0x26)**，再试 WUPA(0x52)。部分克隆卡只应 REQA。
- 刚选完卡就认证，第一次有相当概率失败，重新选卡再来一次就稳。
  读路径重试一次，字典穷举也重试一次——但**只重试「没定论」那几种**
  （卡没应答 `NODATAERR`、收到坏帧 `INTEGERR`、碰撞）。卡回了 4 位 NAK
  （`MINFRAMEERR`）说明它明确拒了这次握手，再试一遍结果不会变，
  白花一次完整的射频往返。
