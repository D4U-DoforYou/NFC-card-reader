# 硬件验证工具

这三个脚本要连真机跑，`npm test` 不会执行它们（文件名不是 `*.test.mjs`）。

## 准备

先起一个 BLE 转发进程：网页端的代码走浏览器蓝牙，脚本里走 TCP，
两边共用同一套帧格式与协议实现，所以转发的是原始帧。

```bash
cd tmp/audit
../rf_device_platform/host/.venv/bin/python relay.py
```

转发进程会打印 `relay ready on 127.0.0.1:8791`，并占用设备的唯一 BLE 连接。
期间不要再用网页端连同一台设备。

## 跑验证

```bash
cd web
node tests/hardware/live-verify.mjs
```

`live-verify.mjs` 跑的是网页端自己的代码（`src/` 下的真实实现），
依次验证：握手与能力协商 → 按给定密钥读块 → 字典穷举 → 整卡读卡 → dump 往返。

## 解卡验证

```bash
node tests/hardware/live-crack.mjs
```

跑两轮：第一轮字典里只有错误的密钥，应该一个扇区都打不开；
第二轮放进真密钥，应该打开对应扇区，并把数据读出来。

真卡实测（2026-11-15，UID 560CAEE9）：
- 4 把错误密钥 → 8 次尝试，0 个扇区解开 ✓
- 加入 4 把真密钥 → 扇区 0/1/2/3 全部解开，读出的块与已知 dump 一致 ✓
- 卡片布局判定为「非标准布局」——这张是 UID / FUID 克隆卡，第 0 块存的是 UID ✓

> 一轮下来 64 次认证花了约 6 分钟：每次认证都要复位射频场、重新选卡，
> 再让芯片跑完 Crypto1 握手。这是硬件决定的，不是实现问题。

## 两个诊断脚本

node tests/hardware/probe-auth-status.mjs   # 对比正确／错误密钥时控制器报的状态
node tests/hardware/probe-settle.mjs        # 认证后加不同延时，看首试成功率

## 提速验证（2026-11）

```bash
node tests/hardware/verify-speedup.mjs   # 提速了没有，正确性有没有被牺牲
node tests/hardware/profile-wake.mjs     # 一次「试一把密钥」的时间与唤醒次数
node tests/hardware/profile-correct-key.mjs  # 正确密钥的成功率与失败时的错误位
node tests/hardware/compare-gain.mjs     # 接收增益两档的对照
node tests/hardware/try-error-register.mjs  # 作业失败后错误寄存器里还留着什么
```

`verify-speedup.mjs` 会跑五组断言：对密钥必须次次通过、错密钥必须次次不通过、
「对密钥 → 立刻错密钥」时错的那次绝不能被误判成成功、同一把密钥连试两个块都要过、
换一把密钥要重新判定。最后给出提速幅度。

实测结论（UID `560CAEE9`）：

| 场景 | 提速前 | 现在 |
| --- | --- | --- |
| 试一把**对**密钥 | 2100 ms | 1598 ms |
| 试一把**错**密钥 | 约 3500 ms | 1969 ms |
| 「对 → 错」交替时错密钥被误判成成功 | — | 0 次 |

关键结论：

- 错密钥时卡回 4 位 NAK，芯片错误寄存器是 `MINFRAMEERR(0x10)`；卡没应答才是
  `NODATAERR(0x08)`。作业失败时固件不把错误位带回来，网页端自己读寄存器
  （0x0A）来分——只有「卡明确拒了握手」才不重试。
- **接收增益不能降**。降一档之后芯片收不到那 4 位 NAK，错误寄存器变空，
  又得分不清上面那两种情况，于是每把错密钥都白跑两遍。
  对照实测（各 12 次正确密钥 + 8 次错误密钥）：

  | 增益 | 正确密钥 | 错误密钥 |
  | --- | --- | --- |
  | 2（芯片默认） | 12/12 通过，1573–1870 ms | 8/8 不通过，1972 ms |
  | 1（降一档） | 12/12 通过，1578 ms | 8/8 不通过，**3986 ms** |

  降一档错误密钥要多花一倍时间，所以保持芯片默认增益。代价是高增益偶尔会
  收到被噪声弄坏的帧（`INTEGERR 0x03`）——那种错误按「没定论」处理，重试一次
  就行，不能当成密钥不对。
- `MFAUTHENT` 的等待时间必须给到 **300 ms**。100 ms 时卡片应答慢一点就报
  `NODATAERR|PROTERR`（0x0A），认证会被误判成失败。
- 选卡先试 **REQA(0x26)**，再试 WUPA(0x52)。部分克隆卡只应 REQA，
  用 WUPA 会一直收不到应答。
- 已知 UID 时可以直接 `SELECT`（帧里带卡号），省掉防冲突那一轮射频往返；
  但 7 字节 UID 要走级联，不能这么省。
- 复位射频场不可省：卡拒绝过一次握手之后不复位就选不上卡。

> 一轮下来 64 次认证花了约 6 分钟：每次认证都要复位射频场、重新选卡，
> 再让芯片跑完 Crypto1 握手。这是硬件决定的，不是实现问题。

## 实测结论（2026-11）

- `MFAUTHENT` 的等待时间必须给到 **300 ms**。100 ms 时卡片应答慢一点就报
  `NODATAERR|PROTERR`（0x0A），认证会被误判成失败。
- 选卡先试 **REQA(0x26)**，再试 WUPA(0x52)。部分克隆卡只应 REQA，
  用 WUPA 会一直收不到应答。
- 刚选完卡就认证，第一次有相当概率失败（时序问题），重新选卡再来一次就稳。
  读路径由 `readBlocks` 重试一次，字典穷举由 `probeAuthenticate` 重试一次。
- 控制器报射频错误时**不能断言密钥错了**：卡没应答与握手被拒在报错上一样，
  只有「芯片没报错但没建立 Crypto1 会话」才能说明密钥没被接受。
