# 设备协议约定

## 会话

1. 主机发送 `HelloRequest`，声明支持的协议版本。
2. 设备返回选定版本、启动 ID、帧限制和传输方式。
3. 主机请求 `CapabilityList`，并检查所需能力的版本。
4. 主机使用请求 ID 启动作业；设备分配作业 ID，并发送已接受、进度和终态事件。

请求 ID 在同一会话内唯一。重新连接会创建新的会话 ID；旧会话的通知不能完成新
会话中的请求。作业 ID 在单次设备启动期间唯一。事件丢失后的恢复方式是调用
`QueryJob` 查询作业状态；设备保留最近 8 个已完成作业。

## 交付和副作用

- 传输层交付成功不代表操作已经完成。
- 只读操作可根据其能力契约重试。
- 带幂等键的修改操作必须在设备本次启动期间对该键去重。若无法确认操作是否完成，
  返回 `JOB_STATE_RESULT_UNCERTAIN`，绝不静默重放。
- 取消尽力而为。已完成的不可逆操作无法撤销；终态事件必须报告实际结果。
- `deadline_ms` 受设备策略限制，并使用设备单调时钟计算。

## 大数据传输

发送方先提交总长度和 SHA-256，再发送有界数据块。接收方确认下一个连续偏移量和
接收窗口。只有传输 ID、偏移量、序号、长度和 CRC32 都匹配时，数据块才会被接受。
只有总长度和 SHA-256 校验通过后，`TransferFinish` 才成功。未完成的上传不会作为
完整数据交给能力模块。

设备为 OTA 接受 `purpose = "firmware"`。固件块逐块写入非活动应用槽；每块检查偏移量
和 CRC32，完整镜像的 SHA-256 校验通过后才切换启动槽。兼容控制端通过数据传输消息
上传已构建镜像。首次启动时新镜像处于
待回滚确认状态；固件会在启动过程中自行确认，如果新镜像无法启动，Bootloader 会
恢复到上一个槽。

当前 BLE GATT 服务 UUID 为 `0000ff10-0000-1000-8000-00805f9b34fb`，RX 特征 UUID 为
`0000ff11-0000-1000-8000-00805f9b34fb`，TX 特征 UUID 为
`0000ff12-0000-1000-8000-00805f9b34fb`。TX 使用 GATT indication。适配器将 COBS
字节流切分为 ATT 载荷，并在另一端重组。设备每次只发送一个 MTU 分片，收到 ATT
确认后才推进到下一片。通知失败或确认超时时，设备断开连接；控制端可重连并通过
`QueryJob` 查询作业状态。USB Serial/JTAG 在当前实现中不是控制链路；USB 接口保留
用于供电、烧录和 JTAG 调试。逻辑 Protobuf Envelope 与传输方式无关，未来其他传输
可以复用。固件 OTA 在现有 BLE 特征上每次传输一个已确认的数据块。

控制端应限制待处理 BLE 分片和每个作业的事件缓存。队列满时不得静默丢弃数据；重连后
可查询仍在设备作业历史中的状态。

## 能力 ID

`OperationDescriptor.mutating` 表示操作是否会改变设备或标签状态。
`requires_target_confirmation` 单独标记写入所选标签的操作；能力模块写入前必须将
用户确认的 UID 与实际检查到的标签 UID 比较。

ID 使用小写反向域名格式，例如 `org.example.rf.raw` 或
`org.example.display.panel`，且不得重复使用。破坏兼容性的变更提升能力主版本；兼容
性新增提升次版本。操作参数和结果均使用带版本的 Protobuf 消息。

固件通过 `org.example.rf.raw` 提供 RF 场控制和原始帧收发。能力版本 1.1 遵循
CLRC663 数据手册 Rev. 5.4 表 47 和表 48 中的 19 个 RX 与 19 个 TX 预设 ID，覆盖
ISO14443-A/B、FeliCa、表中所列副载波和速率的 ISO15693、EPC/UID、四种 EPC-V2 链路
配置以及 Jewel。`rx_mode` 选择接收预设；可选的 `tx_mode` 选择发送预设。省略时，
TX 使用与 RX 相同的 ID。这样既保留现有 ISO14443-A 106 默认值，也允许使用不对称
预设，例如 RX 使用 ISO15693 52 kbit/s SSC，同时单独选择 TX 预设。控制端可按协议字段
选择 RX 与 TX 模式。

RX/TX 预设会配置控制器的调制、比特率和 CRC 寄存器默认值。帧仍是原始帧：盘点、
选卡、防冲突、ISO-DEP 和卡片专属命令不由固件解释。控制端应在发送非默认模式前检查
能力版本 1.1，避免旧固件静默按 Type A 处理。预设数值和
命名已依据 `CLRC663.pdf` 第 57–58 页和第 137–151 页核对。

能力版本 1.2 增加通用 CLRC663 命令/FIFO 执行和寄存器访问。`execute_command` 仅允许
瞬态控制器命令（IDLE、LOADKEY、MFAUTHENT、RECEIVE、TRANSMIT、TRANSCEIVE、
LOADPROTOCOL、READRNR），并限制超时和 FIFO 大小，同时要求主机确认目标 UID。接口不
开放 EEPROM 写入或已存密钥命令。寄存器读取不能消耗 FIFO 数据；写入仅限协议/定时器
寄存器和 Crypto1 状态清除。帧 API 通过 `tx_last_bits` 和 `rx_align` 管理 TXDATANUM 与
RXBITCTRL。驱动拥有的 RF 场和 TxAmp 寄存器仍受保护。控制端可组合这些受限原语实现
更高层协议，无需为每种卡型扩展固件接口。

固件无法从任意原始帧独立验证控制端确认的 UID。控制端必须在发送任何修改帧之前重新
选卡并比较 UID；同时应限制可写区域，避免覆盖制造商块或扇区访问控制数据。

## 安全

BLE 控制应使用加密且已绑定的链路。原始 RF 操作可以承载任意卡片命令，因此控制端发送
写操作前必须取得明确授权，并将操作绑定到已选中的目标 UID。结果详情和诊断日志不得
包含秘密。当前 OTA 传输检查数据完整性；只有启用 Secure Boot V2 后，ESP-IDF 才会在
OTA 收尾阶段验证应用镜像签名。
